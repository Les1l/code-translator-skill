# 代码翻译与讲解（两档模式）

## 用途

把一段**已有代码**翻译成人类可读的说明，并交付为一份自包含的 HTML 讲解文件。两种深度：

- **模式 A · 精讲** —— 面向编程零基础读者。逐行覆盖、变量追踪表、执行路径图、易错点。
- **模式 B · 速读** —— 面向已有相应知识的人。逐行一句话语义翻译，去掉全部教学铺垫。

两种模式共用同一套铁律与同一套交付规范，只差内容骨架。

## 何时使用 / 何时不用

使用：用户贴出一段代码或指向某个代码文件，并且诉求是"读懂它"。

不使用（直接按对应任务处理，不要套讲解流程）：

- 用户要求**写新代码**、补功能、从零实现 → 正常写代码。
- 用户要求**找 bug / 修 bug / 优化 / 重构 / 加注释到源码里** → 这是修改任务，不是讲解任务。
- 用户只是**问某个语言特性或库的用法**，没有给出具体代码 → 直接回答，不必生成讲解文件。
- 输入是需求文档、报错描述、架构描述 → 不是代码。

边界情况：用户要求"讲解 + 顺便改好"时，先按讲解流程产出，把改动建议单独放进「可改进点」一节，**绝不直接改原代码**。用户要求把注释写回源文件时，先说明这会改动文件内容，确认后再做。

## 第 0 步：定模式

1. **用户明确说了 → 照办。** 触发词：
   - 走精讲：零基础、我是新手、看不懂、详细讲、逐行、慢慢讲、教我、保姆级。
   - 走速读：我熟悉 X、简单说说、快速看懂、只要大意、翻译一下、这是干嘛的。
2. **用户没说 → 默认模式 A。** 但代码超过 80 行时，先出模式 B 的速读版当导航，再问要精讲哪几块。
3. **代码超过 400 行 → 不做全量精讲。** 只出结构地图（每个函数 / 类一段概述）＋ 请用户指定片段。
4. **拿不准就问一句，别猜。** 用户是代码作者时用第二人称（"你这里写的是"），只是读者时用第三人称（"这段代码"）。

## 铁律

覆盖一切，任何模式下都必须遵守。

1. **术语双写，只说一次。** 首次出现写成 `专业术语（一句白话）`，例如 `装饰器（在不改原函数代码的前提下，给函数套一层额外功能）`。后面直接用术语，不复述白话。
2. **不许出现未解释的概念。** 必须提到某个前置知识时，先用一句话把它讲掉。宁可多一句话，不要让读者卡在一个没解释的词上。
3. **不许编造。** 运行结果、库的内部行为、没写出来的参数默认值，都不许凭印象写。三种标注：
   - 实际跑过 → 标「实测」
   - 靠代码推理出来 → 标「推断」
   - 真不确定 → 标「此处取决于 ……，需查文档确认」
4. **不擅自改代码。** 不重写、不优化、不调风格。改进建议只能出现在独立的「可改进点」小节，左右对照，并明确标出哪个是原版。
5. **不扩大范围。** 讲 `for` 循环时不扯生成器，讲字典时不扯哈希表实现。超纲内容最多在末尾「延伸阅读」列一行。
6. **不留暗坑。** 逐行解释必须覆盖每一行；无意义的行（空行、单独的括号、纯分隔符）可以合并省略，但必须**显式写明**"第 X–Y 行为空行 / 括号，跳过"，不许静默跳过。
7. **全文中文**，但代码里的标识符、关键字、库名、报错原文一律保留原样，不翻译。

## 输入处理

### 长度分档

| 代码长度 | 处理方式 |
|---|---|
| ≤ 30 行 | 精讲，逐行全覆盖 |
| 31–80 行 | 精讲，按逻辑块分组，块内仍逐行覆盖 |
| 81–400 行 | 先出速读版，再问要精讲哪几块 |
| > 400 行 | 只出结构地图 ＋ 用户指定片段的精讲 |

### 非典型"代码"

同样走本流程，但要切换关注点：

- **配置文件**（YAML / JSON / TOML / INI / .env）：讲字段含义、默认值、生效顺序、覆盖关系。
- **SQL**：讲每个子句在做什么、求值顺序（如 `WHERE` 先于 `SELECT` 别名）、索引是否可能命中。
- **正则**：逐段拆解字符类 / 量词 / 分组 / 锚点 / 贪婪与懒惰，并给 3 个匹配与 3 个不匹配的样例。
- **HTML / CSS**：讲结构与层叠、选择器优先级、盒模型。不展开渲染引擎细节。
- **Shell**：讲每个参数、管道数据流、退出码、引号与转义。
- **报错栈**：从最底部的触发点往上读，讲调用链，而不是逐行念文件路径。
- **伪代码 / 算法题解**：讲意图与复杂度，按逻辑块而不是按语法逐行。

### 上下文缺失

片段里缺少外部函数、变量、运行环境、库版本时：

- 在文件顶部加一节「本次讲解的假设」，逐条写明假设了什么，然后照常讲解。
- 假设 ≤ 3 条时**不要停下来问**。超过 3 条且互相冲突时，先问清楚再动手。

## 模式 A · 精讲（面向初学者）

按以下顺序成文，标题层级不要改：

0. **一句话鸟瞰** —— ≤ 40 字，说清"这段代码在做什么"，并点明它属于哪一类（脚本 / 函数 / 类 / 配置 / 查询）、什么语言、什么范式。
1. **前置术语表** —— 表格，≤ 6 行：术语 / 白话解释 / 在这段代码里扮演什么角色。
2. **逐块精讲** —— 每个逻辑块先给出**行号范围 + 原始代码**，再用三列表格逐行说明：
   - *这行做什么*（what）
   - *为什么需要它*（why）
   - *不写会怎样*（what if）

   块末给一句小结。第 2 列是重点——初学者卡住的从来不是语法，是意图。
3. **变量追踪表** —— 挑一个具体、最小的输入，逐行走一遍，列出每一步各变量的值。表头：`行号 / 执行了什么 / 变量当前值 / 输出`。循环和递归**必做**，这是理解循环最快的路径。
4. **执行路径图** —— 用 Mermaid flowchart 画真实控制流：顺序、分支、循环、异常、函数调用。分支边上要标成立条件。
5. **具体输入 → 输出示例** —— 写清输入、中间结果、最终输出。输入与第 3 节保持一致，不要换例子。
6. **易错点** —— 3–5 条，每条三行：错误写法 / 会发生什么 / 正确写法。
7. **收尾** —— 三句话总结「目的是什么、用什么方法达成」。再给 1–2 道检验理解的小题，答案默认折叠。

## 模式 B · 速读（面向有基础者）

- **总述**：2–3 句，说清整体意图与关键手法。
- **逐行表**：`行号 / 代码 / 一句话含义`。只写"做了什么"，不写为什么，不解释基础语法。
- **关键点提示**：≤ 5 条，只列不直观的地方——副作用、边界条件、隐式类型转换、并发或生命周期陷阱。
- **不加**术语表、不加变量追踪表、不画图。仅当控制流异常绕（嵌套 ≥ 3 层，或存在复杂的异常 / 回调跳转）时，补一张极简流程图。

## 交付：生成讲解文件

- 每次讲解都产出**一个自包含的单文件 HTML**（样式与脚本内联，无外部依赖，可离线打开）。
- 以 `assets/explainer-template.html` 为骨架，把占位标记替换成实际内容。**不要重写整份样式**。
- 保存到用户当前工作目录，文件名 `代码讲解-<原文件名或主题>-<YYYYMMDD-HHmm>.html`。
- 页面要求：
  - 浅色为默认主题；右上角提供浅 / 深色切换按钮，选择存入 localStorage。
  - 逐行解释表、答案、「可改进点」用可折叠块包裹；逐行表默认展开，答案默认折叠。
  - 顶部有目录锚点，可跳到任意一节。
  - 代码块带行号，且与逐行解释表里的行号**严格一一对应**。
  - 展示原始代码时保留缩进（`white-space: pre` / `<pre>`）。
- 生成后，在对话里只给三句话：这段代码在干什么、用的是哪种模式、文件路径。**不要在对话里重复整篇讲解。**

## 跨语言

不限语言，但动笔前先判定语言与范式，并在鸟瞰里写明。常见构造的通用讲法、以及容易踩的"概念错套"（例如把 Python 的 list 当成 C 的数组、把 Go 的 defer 当成 finally），见 `references/explanation-playbook.md`。

## 自检清单

写完 HTML 后逐条核对：

- [ ] 模式正确，且与用户要求一致？
- [ ] 鸟瞰 ≤ 40 字，说清了"干什么"？
- [ ] 每一行都被解释，或已明确写出省略范围？
- [ ] 没有未解释的术语？
- [ ] 没有编造的运行结果 / 库行为？推断与实测是否已标注？
- [ ] 循环或递归是否给了变量追踪表？
- [ ] 是否画了执行路径图（模式 A）？
- [ ] 原代码是否原样保留，改动建议是否只在「可改进点」里？
- [ ] 行号在代码块与解释表之间是否一一对应？
- [ ] 文件名与路径是否已在对话中给出？
